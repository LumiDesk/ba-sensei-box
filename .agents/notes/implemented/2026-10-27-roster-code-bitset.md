# Agent Note: 名单码使用 order 位图

Status: implemented

## Problem

用户勾选 100–200 个学生后，需要一个能直接粘到聊天里的短码，而不是几百个 ID 或一长串 JSON。码还要能跨设备导入、在数据更新后继续可用，并且不能包含账号信息。

## Decision

名单码格式：

```text
SB1-<Base64URL(bitset + 1-byte checksum)>
```

- 位图长度由当前最大 `order` 决定：266 人 → 34 字节；
- 位索引是 `student.order`，不是数组下标；
- 末尾追加 1 字节校验和：`hash = (hash * 31 + byte) % 256`；
- 解码时未知 `order` 的位收集为 `unknownOrders`，UI 提示后忽略；
- 不编码 UID、等级、备注；这些只进可读文本/JSON。

当前 266 人时，码长约 51 字符。

## Alternatives considered

**逗号分隔的 ID 列表。** 100 个 ID 约 600 字符，粘贴/核对都麻烦；位图短一个数量级。

**压缩 JSON + Base64。** 仍然比位图长，且解析更复杂；名单码不需要携带名称。

**把整个名单写进 URL hash。** 链接很长，聊天客户端可能截断；且用户复制的是“码”，不是页面地址。

**不加校验和。** 少 2 个字符，但复制漏字符会静默解出错误名单；校验和值得。

**按数组下标编码。** 数据追加/删除会整体错位；按 `order` 编码允许空洞和增量更新。

## Consequences

- `order` 成为持久化契约，数据同步只能追加，不能重排/删除/复用。
- 码只表达“拥有”，不表达星级/专武/等级；这些需要后续在对话里补充。
- 旧码在新版本中仍可解；新码在旧版本中会忽略未知位，不会报错。
- 修改格式必须新增 `SB2-` 前缀并保留旧解码测试。
